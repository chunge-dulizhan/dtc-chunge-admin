## 五、两级动态结构设计（核心方案）

### 5.1 存储方式选型

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. 新增 D1 表 `roadmap_stages` / `roadmap_topics` | 需迁移 + 后台管理页，超出本阶段范围 | ❌ 需另行审批 |
| B. 塞进 `settings` 键值（一段 JSON） | 无迁移，但后台设置页无法编辑长 JSON，易出错 | ⚠️ 可作备选 |
| B'. 复用 `content_categories` 分类表 | 语义不符，会污染分类数据 | ❌ |
| **C. 独立配置文件 `public/data/roadmap.json`** | 无数据库变更、无后台改动；改文件即改内容；前后端共用同一份 | ✅ 推荐 |

### 5.2 数据结构（建议）

```json
{
  "version": 1,
  "updated_at": "2026-11-08",
  "stages": [
    {
      "id": "s1",
      "name": "产品与市场验证",
      "summary": "先确认有真实需求，再决定做什么产品。",
      "order": 1,
      "visible": true,
      "topics": [
        { "id": "s1-t1", "name": "市场需求研究", "description": "", "order": 1, "visible": true }
      ]
    }
  ]
}
```

- 一级：`id / name / summary / order / visible`（阶段可增删改名改序、可拆分合并=新增两条+删除原条）
- 二级：`id / name / description / order / visible`，通过嵌套归属阶段（改变所属阶段=移动对象，自动保持关联）
- 渲染端只按 `order` 排序、跳过 `visible=false`，**不假设数量**。

### 5.3 渲染方式

- 首页：`site.js` 新增 `renderRoadmap()`，`fetch('/data/roadmap.json')` 后按阶段生成时间轴/卡片，内部 topic 生成列表；无数据时显示空状态。
- 若未来某页面需服务端渲染：Worker 可通过 `env.ASSETS` 读取同一 JSON，**单一数据源，不在模板重复**。
- 视觉：纵向时间轴（阶段序号自动生成 01/02…，超过 6 个阶段自动换列/堆叠），移动端单列；topic 数量自适应网格（`auto-fit`），不设固定条数。

### 5.4 验证方式（子任务4）

临时把 JSON 改为 4 阶段 / 6 阶段、某阶段 3 条 / 12 条 topic，桌面+移动端截图核对，再恢复正式配置；并加自动化测试：读取 JSON 校验结构（id 唯一、order 整数、topics 归属正确），渲染函数对 4/5/6 阶段输入均不报错。
